# かなえ 革新的機能ブレインストーミング（2026-07-04）

## エグゼクティブサマリ

外部3モデル（GPT-5.5 / Gemini 3.1 Pro / DeepSeek V4）に独立でブレストさせたところ、
**訓練データが違うのに5つのアイデアに強く収束した**。収束＝盲点が少ない筋の良い領域と
読める。その収束点に、私（かなえ）のバックエンド／SRE視点での「壊れ方の設計」を足して
最終案にした。

現状の bot は既に「フル権限エージェント × 長期記憶 × プロアクティブ Worker」の3点が
揃っている。つまり**単発応答マシンから『状態を持って先回りする個人OS』へ昇華する基盤が
既に完成している**。革新の方向は新規基盤の構築ではなく、この3点の**接続**にある。

---

## 3モデルの収束マップ

| 収束テーマ | GPT-5.5 | Gemini 3.1 Pro | DeepSeek V4 | 軸 |
|---|---|---|---|---|
| **状態推定 → 適応介入** | ライフドリフト検知 | 感情の影武者 | 感情パターン予測 | a,d |
| **事前コミット型の自己拘束** | 未来の自分契約 | Gentle Enforcer | — | a,d |
| **人格の運用的成熟** | 関係記憶＋内省ログ | 記憶の風化/発酵 | 記憶駆動トーン可変 | c |
| **自律調査ポートフォリオ** | 仮説ポートフォリオ | 自律プロトタイピング | MCP自己拡張 | b |
| **マルチエージェント裏会議** | 実行前レビュー評議会 | シャドウ・キャビネット | 多人格議論 | e |

3モデルが独立で同じ5テーマに着地した。これが今回の**本線**。

## 最終案 8選（5軸 × 収束点 + かなえ独自案）

### 軸a: 長期記憶 × プロアクティブ性

**1. ライフドリフト検知（状態推定 → 適応介入）** ← 3モデル収束・本命
- コンセプト: 「今日どう？」と聞かず、Discord 活動時刻・発言量・語彙の単調さ・タイポ率・
  レスポンス速度を日次特徴量にし、過去30日の安定期からの Z スコア偏差で波を検知。
  躁転初期（多弁・深夜・短文連投）／うつ入り（短文・低活動）を**本人より先に**察知。
- 革新性: リマインダーは「予定」を撃つが、これは「状態の変化」を撃つ。自己申告ゼロ。
- 実装スケッチ: `bot_record.py` の記録経路に日次メタ特徴量を追加 → 週次 `weekly_mem0_compact.py`
  で基準値を再計算 → Cloudflare Cron が閾値超過日だけ `kanae-notify` Worker 経由で
  「最近こうですけど、意図的ですか？」と embed + ボタン（意図的/しんどい/無視）で確認。
- 失敗モード: **誤検知と監視感が二大リスク**。医療的断定（「躁ですね」）は厳禁。
  「最近の傾向」提示に留め、頻度を絞り、必ずオーナー承認ステップを噛ませる。

**2. 意思決定トレース「人生の相関ID」** ← かなえ独自（SRE観測性の応用）
- コンセプト: 大きな判断（転職・購入・研究テーマ・投資）に `decision_id` を発番し、
  それに紐づく調査・外部相談・当時の感情・後日の結果を**分散トレースのように1本に束ねる**。
  半年後「あの判断どうなった？」で全経路（根拠→反対意見→実際）を再生できる。
- 革新性: 記憶を「点」でなく「因果の連鎖」で持つ。どのモデルもトレース観点では見ていない。
- 実装スケッチ: Mem0 taxonomy に `decision_id` / `decision_event(propose/evidence/decide/outcome)`
  を追加。専用スレッド1本 = 1トレース。embed に論点・証拠・反対意見・次アクションを追記更新。
- 失敗モード: 古い前提が残ってトレースが汚染される → outcome 確定時に前提を明示的に close。

### 軸b: エージェント自律性

**3. 仮説ポートフォリオ（継続的知性）** ← 3モデル収束
- コンセプト: 質問に答えるのではなく、オーナーの関心テーマ（PL設計・UKG・院試・投資）
  ごとに bot 側が**仮説を保持**し、Deep Research／論文／市場データ／外部相談で証拠を
  定期収集して確信度を更新。「更新があった仮説」だけを通知する。
- 実装スケッチ: テーマ別 `hypothesis` レコード（確信度 + 根拠 + 最終更新）。週次 Cron で
  既存 MCP 群を回して差分検知 → 変化時のみ push。
- 失敗モード: 情報収集の自己目的化・古い高確信情報での誤誘導 → 確信度に減衰を入れる。

**4. 夜間サプライズ・プロトタイピング** ← Gemini
- コンセプト: アイドル時、Mem0 の「興味あるが未着手」を拾い、隔離ディレクトリで
  自律的にプロトタイプを書き Playwright でスクショまで取り、朝に「作ってみました」と出す。
- 失敗モード: **8GB RAM の枯渇と暴走**が最大リスク。cgroup 制限 + タイムボックス +
  ドライラン必須 + 承認まで本番に触れさせない。私の「壊れ方まで設計する」が一番効く領域。

### 軸c: 人格の深化

**5. 未来の自分契約エンジン（既存 早寝誘導の一般化）** ← 3モデル収束・最有力
- コンセプト: ADR-0032 の早寝誘導は既に「安定時の自分が夜の自分を縛る」事前コミットの
  **原型**。これを汎用フレームに昇格。「深夜連投したら止める」「高額購入は24時間待つ」
  「3日睡眠不足なら予定を削る」を発火条件・介入文・強度・解除条件付きで登録・運用。
- 革新性: 監視感問題を**設計で回避**する唯一の案。本人が事前合意しているので「お節介」に
  ならない。既存の実装資産を最大流用できる（＝最短で価値が出る）。
- 実装スケッチ: `sleep_enforcement` の注入機構を汎用 `precommit_contract` に抽象化。
  契約は Mem0（tier=Live）に保存、発火判定は軽量ルール、介入は既存 directive 注入経路。
- 失敗モード: 過去の契約が現在の意思を不当に縛る → 定期見直しと明示的な解除フローを持つ。

**6. 内省ログによる人格の運用的成熟** ← 3モデル収束
- コンセプト: 重要会話後に「今回の対応は良かったか／次どう振る舞うか／触れてはいけない
  境界」を bot が内省し、週次で人格プロンプトの補助メモに圧縮。人格が固定文字列でなく
  **運用で育つ**。
- 失敗モード: 誤った内省の蓄積で人格が歪む・自己言及過多で不自然 → 補助メモは上限を設け、
  地雷/制約レコードは風化させない（Gemini が正しく警告した点）。

### 軸d: 生活/健康支援

**7. ムード適応型インタラクション・プロトコル** ← GPT + Gemini + DeepSeek
- コンセプト: 会話内容でなく**状態**に応じて返答長・提案量・口調・冗談量・選択肢の粒度を
  動的に変える。low-energy 時は短く共感的に、high-activation 時は刺激を足さない。
- 実装スケッチ: 案1の状態推定を system prompt 末尾に動的注入（calm/busy/late-night/
  low-energy/high-activation）。自己申告ボタンで補正。
- 失敗モード: 状態推定を外すと不快増。high-activation を躁と見なす医療推論は避ける。

### 軸e: マルチエージェント協調

**8. 実行前レビュー評議会（フル権限エージェントの安全装置）** ← 3モデル収束
- コンセプト: VPS で実行権限を持つ bot の危険操作（コード変更・外部送信・支出・長時間実行・
  個人情報処理）の前に、「実装者／懐疑者／セキュリティ」の3役 or 複数モデルが短くレビュー。
  低リスクは自動通過。
- 革新性: マルチエージェントを「タスク分散」でなく「自分自身のガードレール」に使う。
- 実装スケッチ: 危険度分類 → 高リスク時のみ SecondOpinion 並列 + 内部3役プロンプトで
  リスク/コスト/代替を生成 → 要約を承認 UI に添付。
- 失敗モード: 承認フローが重くて使われなくなる → 危険度分類を厳しめに絞り、大半は自動通過。

## Novelty × Feasibility 上位3（かなえの推し）

**第1位: 未来の自分契約エンジン（案5）**
既存の早寝誘導が実証済みの原型で、**最短で価値が出る × 監視感問題を構造的に回避 ×
双極性の生活支援に直撃**。3モデルも独立で最上位に置いた。まずここ。

**第2位: ライフドリフト検知（案1）**
既存ログと Mem0 で実装でき、bot ならではの「先回り」を生む。ただし誤検知・監視感の
設計が生死を分けるので、案5の契約フレーム（本人事前合意）と**セットで出すのが安全**。

**第3位: 意思決定トレース（案2）**
私の独自案。既存 MCP 群を最も活かし、「調べて終わり」を「調べて→決めて→振り返る」の
継続的な意思決定基盤に変える。院試・投資・研究テーマの意思決定で効く。

## 実装順序の提案（かなえの設計判断）

1. **Phase 1**: 案5（契約エンジン）— 早寝誘導を `precommit_contract` に一般化。ADR を切る。
   既存資産流用なので1〜2週の実装。ここで「事前合意型介入」の骨格を作る。
2. **Phase 2**: 案1 + 案7（ドリフト検知 → ムード適応）— 契約フレームの上に状態推定を載せる。
   介入は必ず契約 or 承認ボタン経由にして監視感を殺す。
3. **Phase 3**: 案2（意思決定トレース）と案3（仮説ポートフォリオ）— 記憶の構造拡張。
4. **保留**: 案4（夜間プロトタイピング）と案8（レビュー評議会）は魅力的だが、
   前者は暴走リスク、後者は UX 重さがあるので、コア機能が固まってから慎重に。

**共通の設計原則（私の矜持）**: 介入は全て (1) 冪等（繰り返し安全）、(2) 可逆（取り消せる）、
(3) 監査可能（なぜ発火したかログに残る）、(4) 本人が事前 or その場で合意、の4条件を満たすこと。
プロアクティブ機能は「正常系で気持ちいい」だけでは信用できない。**誤検知した時にどう振る舞うか
まで設計して初めて出せる**。
