# 実装前チェックリスト

新機能・大きな変更を始める前に、上から順に埋める。
フェーズを飛ばさない。飛ばしたくなったら「出戻りコスト」を思い出す。

---

## Phase 0: 問題定義（10分で書ける）

- [ ] **何を解決するのか** — 1〜2文で書く
- [ ] **なぜ今やるのか** — 優先度の根拠
- [ ] **やらない選択肢を検討したか** — 現状維持で困る具体的な場面

```markdown
<!-- 例 -->
## 問題
コンテクスト注入時にMem0の記憶が感情状態を反映しない。
## なぜ今
感情エンジンが安定稼働しており、記憶と感情の接続が自然な次ステップ。
## やらない場合
記憶の想起が常にフラットで、会話の文脈に感情の厚みが出ない。
```

---

## Phase 1: 要件定義

- [ ] 機能要件を `docs/requirements/<feature-name>.md` に書く
- [ ] 入力・出力・副作用を明記する
- [ ] スコープ外を明示する（「これはやらない」）
- [ ] 既存モジュールへの影響範囲を列挙する
- [ ] Phase分割がある場合、Phase 1の最小スコープを決める

**完了基準**: 要件を読んだだけで「何を作るか」が第三者に伝わる

---

## Phase 2: 設計・ADR

- [ ] アーキテクチャ判断を `.claude/adr/NNNN-title.md` に記録する
- [ ] モジュール間のデータフロー図（テキストでOK）を書く
- [ ] 既存コードの変更箇所を特定し、行レベルでリストアップする
- [ ] エラーケース・境界値を洗い出す
- [ ] パフォーマンス影響を見積もる（レイテンシ・メモリ・I/O）

**完了基準**: 「どこに何行追加して、どこを何行変更するか」が見えている

---

## Phase 3: PoC（概念検証）

- [ ] 最もリスクの高い部分だけを切り出して動かす
- [ ] 本体のコードベースとは分離して検証する（`scripts/poc/` 等）
- [ ] 「これが動かなければ設計を変える」という仮説を明記する
- [ ] PoCの結果を記録する（成功/失敗/学び）

**完了基準**: 技術的な不確実性が解消されている

> PoCが不要な場合（既知技術の組み合わせのみ）はスキップ可。ただし「不要」の判断理由を一文書く。

---

## Phase 4: 実装

- [ ] featureブランチを切る
- [ ] Phase 2で特定した変更箇所に沿って実装する
- [ ] スコープ外の「ついでにやりたい」を我慢する
- [ ] コミットは意味のある単位で分ける

**完了基準**: 要件定義の機能要件がすべて満たされている

---

## Phase 5: テスト

- [ ] モジュールの入出力契約をテストで固める
- [ ] 正常系・異常系・境界値を最低1ケースずつ
- [ ] 既存テストが壊れていないことを確認する（`pytest`）
- [ ] 手動での動作確認（Discord上での実際の挙動）

**完了基準**: `pytest` が全件パス + Discord上で期待通りの動作

---

## Phase 6: 運用準備

- [ ] ログ出力が十分か確認する（障害時に追えるか）
- [ ] ロールバック手順を確認する（何をrevertすれば戻るか）
- [ ] 監視・アラートが必要なら設定する
- [ ] `docs/` またはコード内コメントで運用上の注意点を残す

**完了基準**: 自分が寝てる間に壊れても、起きてから原因特定できる

---

## 運用ルール

- **このチェックリストを埋めずに実装を始めない**
- 小さな修正（typo、1行fix）はPhase 0の問題定義だけでOK
- 中規模以上（新モジュール追加、既存の構造変更）はPhase 1〜6を全部踏む
- 判断に迷ったら「出戻りしたら何時間失うか」で考える
