## 実装した動作。

`services/codex_app_server/turn_hooks.py` が、1回のDiscord依頼に閉じた状態を保持します。`session.py` のイベント処理から呼び出します。グローバルなCodex設定や、開発用エージェントのhook設定は変更していません。

### 失敗反復時の方針修正。

- `commandExecution`、`fileChange`、`mcpToolCall`、`dynamicToolCall` の終了状態を観測します。
- 同じ操作・同じ引数の失敗が、直近12件の対象結果内で3回になった場合、`turn/steer` で方針修正を促します。介入は依頼あたり最大1回です。
- 同じ操作が成功すると、その操作の失敗履歴を解除します。異なる引数の成功は、元の操作の成功とは扱いません。
- 重複通知、正常な繰り返し、承認拒否の反復には再試行を促しません。ネイティブの検索操作のみで構成されたコマンドの終了コード1は、検索結果なしとして除外します。
- steeringの応答待ちは最大5秒です。未対応・終了との競合・応答不明の場合に再送しません。終了時の照合は引き続き実行します。

### 終了前の実行結果照合。

- `turn/plan/updated` の最新の計画と、各操作の最新の結果を照合します。
- 失敗したままの操作、または未完了手順が残る場合だけ、同じthreadで確認用のターンを最大1回実行します。モデル、reasoning effort、権限設定、会話のロック、当初の終了期限を維持します。
- 元の依頼やツール呼び出しを再送しません。既存の記録を確認し、残作業の実施、代替手段で完了した説明、または未完了事項の報告を求めます。
- 操作失敗は副作用がなかった証拠ではありません。書き込みや送信を繰り返す前に状態確認を行い、完了済み操作の再実行・拒否済み承認の迂回をしないよう指示します。
- 最終回答とphase不明の本文は、終了処理までDiscordへの表示を保留します。明示的なcommentaryは継続表示します。採用する回答だけをstream・incrementalコールバックへ渡します。
- 再確認中の中断は、再確認側のturn IDへ伝えます。再確認の失敗時に保留した草稿を配信しません。
- 補助モデル・独立検証用の直接生成セッションは既定で無効です。メイン会話のmanagerだけが有効化するため、検証処理が自分自身を再検証することを防ぎます。

hookの入力には失敗件数と未完了件数だけを使用します。ツールの本文、引数、エラー文、計画の文章を制御指示へ再コピーしません。状態の保持は直近128種類の操作結果、512件の通知ID、12件の反復窓に制限します。次のDiscord依頼へは持ち越しません。

## 設定と観測。

`CODEX_APP_SERVER_TURN_HOOKS_ENABLED` は既定でtrueです。falseにすると、次のプロセス起動から既存の表示・実行経路へ戻ります。追加の依存ライブラリはありません。

```bash
CODEX_APP_SERVER_TURN_HOOKS_ENABLED=false
```

ログには `Codex hook repeated_failure` と `Codex hook completion_review` を出力します。`CodexTurnResult` の `hook_recovery_nudges` と `hook_completion_reviews` から、方針修正の送信試行と再確認の回数を取得できます。ツール引数・本文はこれらのログへ出力しません。

検証対象には、重複通知、同じ操作の成功による解除、別操作との混同防止、承認拒否、検索結果なし、古いturnの通知、最終回答の先行配信防止、確認回数上限、期限、中断、次の依頼への状態非継承、機能無効時の互換性を含みます。

実会話での完了率・誤報率・平均待ち時間は未測定です。モデルが確認指示に従うことや、外部操作の成功を機械的に証明する機能ではありません。正常な代替手段で完了していても、元の操作の失敗が残れば1回再確認します。ツールの構造化状態が成功でも本文に業務上の失敗が書かれているケースや、ネイティブ通知へ露出しない入れ子の操作は、この判定だけでは検出できません。文章の正確性には既存の独立検証が引き続き必要です。

最終本文は正常な会話でも終了通知後に表示するため、最終回答の文字単位の先行表示は行いません。追加ターンが生じた依頼には、その分の待ち時間とモデル使用量が発生します。状態は永続化しないため、プロセス再起動を跨ぐ用件の復元は対象外です。

本番には作業ツリーにない補助モデル・証拠記録等の変更があります。本番反映時は、この追加差分を本番相当のブランチへ統合し、既存の独立検証との組合せを検証する必要があります。古い作業ツリー全体で本番を上書きする運用は想定していません。
